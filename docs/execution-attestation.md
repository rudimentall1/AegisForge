# Execution Attestations

## Purpose

AegisForge execution attestations are detached Ed25519 signatures over canonical claims that bind a local-experiment record to a claimed signer, runner, environment digest, case, runtime round, task, pinned repository revision, issuance time, and caller-supplied nonce.

The attestation is a separate object. The local-experiment ZIP bundle remains an integrity-checked package of the canonical record and raw artifacts. A detached attestation can be verified against that bundle without adding signer-controlled files to the bundle's strict file allowlist.

## Trust boundaries

A successful bundle-aware verification establishes three separate facts:

- `bundle_integrity_verified=true`: the bundle schema, file allowlist, sizes, and raw-artifact hashes were checked.
- `attestation_verified=true`: the Ed25519 signature and claims matched the externally supplied trusted public key, expected signer ID, and exact record embedded in the bundle.
- `replay_protection_verified=true`: the signed `(signer_id, nonce)` pair was atomically accepted by the configured replay registry for the first time.

It does **not** establish that the process actually ran, that the runner was uncompromised, that the environment hash is truthful, that the experiment is reproducible, or that the target has a vulnerability. A signed claim can still be false if the signer or runner is compromised or the signing boundary is incorrectly placed.

Never use a public key supplied inside the attestation or bundle as the trust anchor. The verifier caller must obtain the trusted public key and expected signer ID from an independent trust configuration.

## Create an attestation

The signing boundary is responsible for authenticating the runner before signing. Keep private key bytes in a protected secret store or signer process; do not place them in the repository, experiment record, logs, or exported bundle.

The `create_execution_attestation` function requires these inputs:

- `record`: the canonical local-experiment record.
- `signer_id`: stable identifier for the signing identity.
- `runner_id`: claimed runner identity.
- `environment_sha256`: SHA-256 of a caller-defined, canonical environment description.
- `issued_at`: issuance time as a timezone-aware ISO-8601 timestamp; use UTC, for example `2026-10-22T07:00:00Z`.
- `nonce`: a unique, unpredictable value for that signer, generated by the caller.
- `private_key_bytes`: the 32-byte Ed25519 private key seed.

The returned object contains `claims`, `signature_ed25519`, and the explicit `authenticity=SIGNED_CLAIMS_ONLY` label. Store the detached object as a separately managed file if it needs to travel with the bundle.

## Verify a bundle and reject replay

Use the replay-protected bundle verifier when verifying evidence in an operational workflow:

```python
from shared.attestation_replay import (
    SQLiteAttestationReplayRegistry,
    verify_bundle_execution_attestation_with_replay_protection,
)

replay_registry = SQLiteAttestationReplayRegistry(
    "/var/lib/aegisforge/attestation-replay.sqlite3"
)

report = verify_bundle_execution_attestation_with_replay_protection(
    bundle_bytes,
    attestation,
    trusted_public_key_bytes=trusted_public_key_bytes,
    expected_signer_id="ci-runner-key-1",
    replay_registry=replay_registry,
    max_age_seconds=600,
)

if report["status"] != "PASS":
    raise ValueError(f"Evidence verification failed: {report['errors']}")

# Keep these as separate report fields. Do not promote this to a finding.
assert report["bundle_integrity_verified"] is True
assert report["attestation_verified"] is True
assert report["replay_protection_verified"] is True
assert report["execution_truth_established"] is False
assert report["runner_compromise_ruled_out"] is False
```

The freshness policy is opt-in at the call site. Set `max_age_seconds` when a recent issuance is required; the default permitted future clock skew is 300 seconds and can be set explicitly with `max_future_skew_seconds`. A timezone-aware `now` argument is available for deterministic testing only.

Do not use `verify_execution_attestation` or `verify_bundle_execution_attestation` alone when the caller requires nonce replay prevention. Those functions verify signatures and claims but do not persist a consumed nonce.

## Replay registry requirements

`SQLiteAttestationReplayRegistry` records signer/nonce pairs using an atomic database uniqueness constraint. Reusing a pair fails closed. The registry:

- must use a durable database path, not `:memory:`;
- must be shared by every verifier that belongs to the same replay domain;
- must remain available, otherwise replay-protected verification returns `FAIL`;
- must not be replaced with an empty database during normal operation, because doing so discards replay history.

A local SQLite file is not a distributed replay registry if different machines or workers use independent copies. Deployments with multiple hosts must provide a shared durable replay store or another atomic registry implementation that satisfies the same interface.

Nonce expiry/retention cleanup is not implemented. Removing consumed nonce records can allow archived attestations to be accepted again, so preserve the registry until an explicit retention policy proves that the affected attestations can no longer be valid.

## Remaining trust work

The caller remains responsible for trusted-key distribution, signer authorization, key rotation and revocation, nonce generation, freshness policy, durable replay-store operations, and authenticating the runner before signing. The current mechanism is not hardware attestation or a guarantee from a CI platform identity provider.

A valid report is evidence about package consistency and signed claims only. Vulnerability confirmation still requires an authorized, target-specific reproduction, counter-tests, impact reasoning, and human review under the Research Case release gate.
